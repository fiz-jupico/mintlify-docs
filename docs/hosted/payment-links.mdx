Payment Links let you create a payment request and share it with a customer by any channel — email, SMS, chat, social, or any other communication flow — without requiring the customer to start inside a traditional checkout page.

## When to use Payment Links

Use Payment Links for:

- ad hoc payment requests that don't originate from a checkout flow
- service invoices where you don't need a full invoice workflow
- deposits or partial payments
- support-assisted payments where an agent sends a link mid-conversation
- merchant-generated payment requests outside your standard ordering flow
- payment collection triggered by email or SMS campaigns

## Typical flow

<Steps>
  <Step title="Create a payment link">
    Create a payment link through Backoffice or the API, depending on whether the request is manual or automated.
  </Step>
  <Step title="Configure the link">
    Set the amount, merchant, description, expiration behavior, and allowed payment options.
  </Step>
  <Step title="Share the link">
    Send the payment link to the customer via email, SMS, chat, or any other channel.
  </Step>
  <Step title="Customer pays">
    The customer opens the hosted payment page from the link and completes payment.
  </Step>
  <Step title="Receive or query payment status">
    Your platform receives payment status via webhook events or queries it directly through the API.
  </Step>
  <Step title="Track completion, expiration, or failure">
    Your operations team monitors the outcome — paid, expired, or failed — and takes any follow-up action.
  </Step>
</Steps>

## What to configure

A payment link should define:

- **Merchant or submerchant** — the account to receive the funds
- **Amount and currency** — the payment amount and currency code
- **Payment description** — a customer-facing description of what the payment is for
- **Customer reference** — your platform's reference for the payer or order
- **Expiration behavior** — how long the link stays active before it expires
- **Allowed payment methods** — which options the customer can use to pay
- **Metadata** — key-value pairs for reconciliation and reporting
- **Confirmation messaging** — what the customer sees on the hosted page after completing or abandoning payment

## Request requirements

Every request to create a payment link must include:

| Field | Notes |
| --- | --- |
| `subMerchantId` | The submerchant account that receives the funds |
| `totalAmount` | The authoritative amount charged |
| `amount` **or** `items` | At least one of the two, in addition to `totalAmount` |

`description` is optional on payment links, and so is `hostedSession`. Send every amount as a JSON number — a quoted string such as `"200"` is rejected.

### Choosing between `amount` and `items`

`totalAmount` is always the amount charged. On top of it you must send at least one of `amount` or `items`, which describe how that total is composed:

- Use **`amount`** for a single-figure request, where the customer just owes one sum.
- Use **`items`** when the customer should see line-item detail on the hosted page.

Omitting both returns `At least one of amount or items must be provided`.

<CodeGroup>
```json Single amount
{
  "subMerchantId": "jpt-sim-md-1",
  "totalAmount": 200,
  "amount": 200,
  "description": "Consulting retainer"
}
```

```json Itemized
{
  "subMerchantId": "jpt-sim-md-1",
  "totalAmount": 200,
  "description": "Consulting retainer",
  "items": [
    { "description": "Consulting hours", "quantity": 2, "amount": 100 }
  ]
}
```
</CodeGroup>

When you send `items`, each entry must carry `description`, `quantity`, and `amount` — where `amount` is the price per unit, not the line total — and the figures must reconcile with `totalAmount` exactly:

```
sum(item.amount × item.quantity) + taxAmount + sum(totalModifiers.amount) = totalAmount
```

`totalModifiers` entries carry an `amount`, an optional `description`, and a `type` of `Coupon`, `Discount`, `Fee`, or `Other`.

## Link expiration

`hostedSession.constraints.timeLimit` controls how many minutes the link stays payable, counted from when it is created.

- **Accepted range** — 1 to 259200 minutes, or up to six months
- **Default** — no expiration. Omit `timeLimit` and the link stays payable until you deactivate it.

```json
"hostedSession": {
  "constraints": { "timeLimit": 10000 }
}
```

Note that the field is nested under `constraints`. A `timeLimit` placed directly on `hostedSession` is ignored and the link is still created successfully — without an expiration.

To change the window on an existing link, call **Update a payment link** with a new `timeLimit`. The update shifts the existing expiration by the difference between the new and previous values rather than restarting the countdown from the time of the update.

## Payment links don't redirect

Payment links always open as a standalone hosted page. They have no `flow` configuration and no return URLs, so the customer stays on the Jupico-hosted page after paying rather than being sent back to your site.

<Warning>
  Don't rely on a post-payment redirect from a payment link. Confirm the outcome server-side through webhook events or the query API. If your flow needs the customer returned to a URL you control, use [Checkout](/docs/hosted/checkout) instead — it supports `successUrl`, `cancelUrl`, and `backUrl`.
</Warning>

## Backoffice vs API

<CardGroup cols={2}>
  <Card title="Use Backoffice" icon="display">
    Choose Backoffice when your operations team needs to manually create and send individual payment links — for example, to handle support requests or one-off invoicing scenarios.
  </Card>
  <Card title="Use the API" icon="code">
    Choose the API when payment-link creation should be embedded into your product, triggered automatically from an order, or orchestrated from another workflow in your platform.
  </Card>
</CardGroup>

## Support guidance

Equip your support team to answer customer questions about payment links. Support should be able to confirm:

- whether the link has been paid
- whether the link has expired
- whether the customer attempted and failed payment
- which merchant and order the link belongs to
- whether a refund or a new payment link is needed

<Info>
  **Payment Links vs Invoicing** — Use Payment Links for lightweight, shareable payment requests that don't require invoice identity or accounts-receivable tracking. Switch to [Invoicing](/docs/hosted/invoicing) when the request needs an invoice number, a due date, itemization, or AR lifecycle management.
</Info>
